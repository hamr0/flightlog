## 1. Problem

Errors in the apps I run (addypin, gitdone, latefyi backends) either crash a
process silently or fail in the dark — I find out late or never. Each app handles
errors differently or not at all. Sentry solves this but is the wrong shape and
wrong time for a solo, pre-scale, zero-telemetry builder: its one hard pillar
(aggregation at volume) doesn't matter until I have more errors than I can read
by hand, and its context-capture is the surveillance payload my privacy work
exists to refuse. What I actually need is the ~20-line global error net,
packaged once so it wires into every app the same way.

## 2. Goal

A zero-dependency Node library that catches the errors my apps would otherwise
lose and appends each as one JSON line to a local JSONL file I can read at any
time — even on a healthy app — to see *where things have failed*.

- **Nothing disappears** — every error lands somewhere findable.
- **Jumpstart to the failure** — a predictable local JSONL I reach into anytime.
- **One net, everywhere** — identical, audited handling across all my apps.
- **Silent + lightweight** — never becomes the bug, never phones home, zero deps.

## 3. Success criteria (how we know it worked)

1. Wiring an app to it is ≤ 3 lines and adds **zero** production dependencies.
2. All four capture cases land one correct JSONL line: uncaught, unhandled
   rejection, manual `capture()`, and non-Error thrown values.
3. A long-running server cannot fill its disk via the log (bounded by rotation).
4. A broken sink (perms/disk/readonly) never crashes the app **and** is never
   silent (one stderr warning).
5. The file is readable by `tail`/`jq`/editor with no special tooling.
6. No context is ever captured that the adopter did not explicitly pass.

## 4. What it is NOT (the refusals — these *are* the product)

- **No aggregation / dedup / counts** — scale-gated; `jq` covers it when needed.
- **No breadcrumbs / auto-captured context** — the surveillance payload a privacy
  suite refuses. **Default-out on context, always.**
- **No UI, no server, no reader** — the JSONL *is* the interface. A thin CLI
  reader may bolt on later iff BYO-`jq` proves annoying; format won't change.
- **No symbolication / alerting / release tracking** — team/scale process.
- **Not a general logger** — errors only; no info/warn levels (pino/winston
  territory). Possibly revisited, not on spec.
- **No restart logic** — crash-loop backoff is the supervisor's job.

## 6. Public API (whole surface)

```js
import { install } from 'flightlog';

const { capture, captureSync } = install({
  file: '/var/log/addypin/errors.jsonl', // sink; omit → stderr
  context: { app: 'addypin', release: 'v1.4.2' }, // static, adopter-chosen
  exitOnUncaught: true,   // default; false = log-and-stay-alive (CLI/desktop)
  exitOnRejection: false, // default; true = log (sync) then exit(1) on a rejection
  bootCheck: true,        // default; false = warn (don't throw) if the sink is unwritable at boot
  maxBytes: 5_000_000,    // confirmed default: 5 MB; 0 = disable rotation
});

try { risky(); } catch (err) { capture(err, { where: 'checkout', userId }); }
```

- `install(opts?) → { capture, captureSync }` — registers global handlers, runs
  boot-time writability check, returns both capture functions.
- `capture(err, extra?)` — async; normalize any thrown value, append one line with
  `{ ...context, ...extra }`. Fire-and-forget.
- `captureSync(err, extra?)` — synchronous sibling for capture-then-exit (§14).

**Record shape:**
```json
{"ts":"...","kind":"uncaught","name":"TypeError","message":"...","stack":"...","app":"addypin","release":"v1.4.2"}
```
`kind` ∈ `uncaught | unhandledRejection | manual`. Everything after `stack` is
adopter-supplied context only.

## 7. Error-class model (resolves "keep alive vs fail")

1. **Operational errors** (handler throws, DB fails, bad input) — *expected*.
   Caught at the boundary via `capture()`; that one request fails; **server stays
   up**. This is "keep alive on small forgivable errors."
2. **Uncaught exceptions** — escaped every handler; event loop in unknown state.
   Log (sync) → `exit(1)` → supervisor restarts clean. Keeps firing → supervisor
   backoff gives up after N, stays **down loudly**. This is "major failure →
   better to fail."

## 8. Self-failure handling

Write wrapped in try/catch (never propagates). First failure → one stderr line
naming the errno; `warned` flag prevents spam; reset on next success; stderr
write itself wrapped (failsafe). Likely errnos: `EACCES` (perms/chmod), `EROFS`
(read-only container fs), `ENOENT` (missing dir), `ENOSPC` (disk full), `EDQUOT`
(quota). Boot check (`mkdirSync` recursive + probe append) surfaces a misconfigured
path at startup, not at the first real error.

### 9.6 Threat model (for context.md)
flightlog never harvests context — but the JSONL **will** contain whatever the
adopter passes to `install({context})` / `capture(err, extra)`, plus error
messages/stacks that may incidentally include sensitive strings. Therefore:
adopters own what they put in context; the log file inherits the sensitivity of
its contents (keep it off shared/world-readable paths). This is stated up front so
"local + private" isn't misread as "safe to pass secrets to." **Hardening (added
post-audit):** flightlog creates the log file `0600` (owner-only) by default, so
it isn't group/world-readable on a shared host; the mode applies only at creation.

### 12.1 Known limitations

- **Cross-realm Errors degrade to `{"message":"{}"}`.** `normalize()` detects
  Errors with `value instanceof Error` (the locked M1 contract). An `Error` thrown
  across a realm boundary (`vm` context, `worker_threads`) is *not* `instanceof`
  the host realm's `Error`, so it falls to the non-Error path → `JSON.stringify`
  yields `{}` (Error fields are non-enumerable) → `message: "{}"` and a synthetic
  (not original) stack. Rare in a single-process Node server, so **accepted, not
  fixed.**
  - *Why not duck-type it* (validated): testing `typeof value.message === 'string'
    && typeof value.stack === 'string'` would mis-classify ordinary thrown plain
    objects (e.g. `{message, stack, code, userId}`) as Errors and **silently drop
    their other fields** — a worse, more common regression than the edge it fixes,
    and it violates *nothing disappears*.
  - *If it ever matters,* widen detection with a brand check (zero-dep, no false
    positives), not duck-typing:
    `value instanceof Error || Object.prototype.toString.call(value) === '[object Error]'`.

## 14. Post-0.1.0 adopter feedback — gitdone (first real integration), 2026-05-31

`gitdone` (CommonJS app, Node 22.22; one long-lived HTTP server + short-lived
per-message/per-cron CLI processes) integrated `0.1.0`. Verdict: core solid; all
gaps are about **short-lived processes**. Three asks, three verdicts — the standing
doctrine (mechanism-in-lib/policy-in-adopter; refusals are the product; no fluff)
arbitrated each. Ships in **0.2.0** (additive, backward-compatible).

1. **`captureSync(err, extra?)` — ACCEPTED (in full).** A short-lived process's
   normal failure is "log, then exit." The async `capture()` line is lost because
   `process.exit()` kills the loop before `appendFile` flushes (deterministic empty
   file). The sink already has a synchronous writer (`writeSync`); it was only wired
   into the uncaught path. Surfacing it as `captureSync` is the *exact* locked split
   — flightlog guarantees the write lands; the adopter keeps the exit code. No new
   mechanism, no taxonomy change (`kind` stays `manual`), zero new surface to
   secure. Chosen over an awaitable `capture()` because that makes every short-lived
   call site remember to `await` — `captureSync` is the smaller footgun.

2. **`exitOnRejection` (default `false`) — ACCEPTED (with care).** This touches a
   *litigated refusal* ("rejections log only and do NOT exit"; CLAUDE.md says don't
   re-add without re-opening this PRD — hence this entry). Read precisely, the
   refusal governs the **default**, and the default is unchanged. By registering an
   `unhandledRejection` handler flightlog *actively* suppresses Node's crash, so a
   short-lived process exits `0` — which a mail pipe reads as "delivered" and
   silently drops a failed message (gitdone's real bug). The opt-in knob mirrors
   `exitOnUncaught` exactly; when `true` it writes **synchronously** then `exit(1)`,
   which also resolves the non-determinism (the async survival the adopter saw was
   luck). Default-`false` preserves the long-lived-server contract verbatim.
   Mechanism in lib, policy in adopter: *the adopter* declares their process
   short-lived. **Not** re-adding a refused feature — adding a documented escape
   hatch with the safe default intact.

3. **CJS dual-build — DECLINED; honest docs instead.** flightlog is ESM-only by
   locked decision (§5, §9.1: the `.js` authored is the `.js` shipped). A dual
   build / CJS entry adds an artifact + a second condition + maintenance — the
   "cater to everyone, end up with fluff" the project refuses. `engines: ">=18"` is
   **honest for the supported path**: ESM consumers do run on ≥18. Raising the floor
   to 22.12 would falsely exclude the primary ESM-on-18 consumers; a `"require"`
   condition can't point at ESM anyway (same `ERR_REQUIRE_ESM`). The real gap was
   undocumented: CJS `require('flightlog')` works only on Node **≥22.12**
   (`require(esm)` stable). Fix = a prominent ESM-only note + the CJS floor +
   `await import()` fallback in `context.md`/README. `engines` unchanged.
   *Adopters are expected to do this small bit of work; flightlog won't grow a build
   step to avoid it.*

### 14.1 Second-round feedback — fatal boot probe vs short-lived processes (2026-05-31, 0.3.0)

4. **`bootCheck` (default `true`) — ACCEPTED.** gitdone's `receive.js` runs
   per-message as a Postfix pipe; the boot-time writability probe is fatal (locked,
   §8: "fail loud at boot"), so an unwritable log dir makes *every* inbound message
   exit non-zero and Postfix defers *all* mail. Correctly diagnosed as an adoption
   consequence, not a bug: the fatal boot is the **one** intentional exception to
   "flightlog never crashes the app," and it was designed for a long-lived server
   (find out once, at deploy). For a per-invocation process that exception inverts —
   a broken *error sink* takes down the *real work*. So `bootCheck:false` makes the
   boot failure non-fatal: warn once to stderr, then degrade to the existing
   swallow-on-write contract. Same family as `exitOnUncaught`/`exitOnRejection` —
   server-shaped default preserved (`true`), opt-out for the short-lived shape.
   *Nuance recorded for adopters:* for a **mail pipe specifically**, the default
   (defer) is often safer than the opt-out (deliver-blind) — deferred mail is queued
   and retried, not lost — so the knob is the general fix, not blanket advice to flip
   it. Confirmed needed across the user's stack (multiple Postfix-fronted apps), so
   it belongs in the library, not patched per-app. Adopter can still get non-fatal
   boot without the knob via `try/catch` around `install()`; the knob removes the
   footgun of having to stub `capture`/`captureSync` on the throw path.

## 15. Second-adopter feedback — plato, 2026-06-01

`plato` (self-hosted forum; one long-lived server plus short-lived cron/pipe
siblings sharing a sink) is the second real integration after gitdone (§14).
Deliberately **left un-worked-around in plato so the boundary stays clean** — four
gaps surfaced as upstream candidates. Same arbitration as §14
(mechanism-in-lib/policy-in-adopter; refusals are the product; no fluff). The
deciding question for each: *does it add library code, or is the mechanism already
there and only docs are missing?* Two are docs, one declined, one a real additive
feature deferred to 0.4.0.

1. **`proc`/role convention — DOC-ONLY (no option).** gitdone and plato both
   hand-rolled a `proc` field in `context` to tell the server apart from cron/pipe
   processes writing the same sink. Real, universal need — but the mechanism is
   *already complete*: `context: { proc: 'server' }`. A first-class `proc` option
   would spread into the record identically to every other context key — redundant
   surface for zero new mechanism, exactly what LIBRARY_CONVENTIONS §1 ("default-out
   on new API surface") refuses; and blessing a key *name* is curation, which the
   doctrine assigns to the adopter. Resolution: a one-paragraph **gotcha** in
   `context.md` blessing `proc` as the conventional key (so cross-app `jq` lines
   up), and an `examples/read.js` `--match proc=cron` example. No code. Same family
   as §14.3 (CJS): honest docs instead of surface.

2. **`safePath()` / request-context redaction — DECLINED (code); doc recipe
   instead.** Every web adopter writes `{ where:'request', method, path }` and must
   remember to strip the query string so tokens/secrets in the URL don't hit disk.
   A shipped `safePath()`/redaction helper is refused on three compounding grounds:
   (a) it **inverts the core identity** — flightlog is a pure pass-through that
   "logs only what you pass"; a redactor makes it start *transforming* adopter data
   and holding opinions about what's sensitive; (b) a redactor that's wrong is a
   **security footgun with flightlog's name on it** — adopters would trust it and
   stop thinking, strictly worse than the threat model's deliberate "you own what
   goes into context"; (c) it **couples flightlog to HTTP** (`method`/`path`/query
   are web-specific; flightlog is framework-agnostic). *But* the threat model
   created an obligation by warning-without-showing, so flightlog owes a **gotcha
   with the safe shape** (`path: req.url.split('?')[0]`, drop headers/cookies) —
   added to `context.md`. Doc, not code. Recorded in CLAUDE.md most-litigated
   refusals so it isn't re-added.

3. **`examples/read.js` — ACCEPTED (repo-only reference; shipped this commit).**
   "No reader ships" (§4, §5) governs the **package** — no `bin`, no runtime reader
   to secure. It does **not** govern `examples/`, which is repo-only by design
   (excluded from `files`). `read.js` is the symmetric sibling to `ship.js` (read
   side ↔ ship side): a zero-dep, copy-and-adapt streaming reader that filters by
   `kind`/`match`/`since`/`tail`, skips torn lines, and **prints the `jq`
   equivalent** under each result so adopters graduate off it. Carries the operator
   discipline the way ship.js carries the upload discipline; consistent with §4 ("a
   thin CLI reader may bolt on later") and §12 ("CLI reader — deferred;
   format-compatible") without committing to a shipped reader. No PRD-scope change.

4. **`captureSync` → status return — ACCEPTED & BUILT in 0.4.0 (additive).**
   *Resolved:* return shape is **`{ ok: boolean, errno?: string }`** (errno included
   only on failure, when the OS gave one); **`captureSync` only** — `capture()` stays
   fire-and-forget `void` (asymmetry documented in `WriteResult`'s typedef and the
   `context.md` API note). `WriteResult` added to `src/types.js`; `sink.writeSync`
   now returns it and `install`'s `captureSync` threads it through; two new tests
   (sink-level ok/ok-false-with-errno; install-level healthy + degraded-sink via
   `bootCheck:false`). 38 tests green, `tsc` clean, `.d.ts` regenerated. Original
   rationale below.
   The strongest *code* candidate and squarely in the §14 family (every accepted
   gitdone ask was "a short-lived process can't tell success from silent-drop").
   Today `captureSync` returns `void` and the sink swallows write failures (warn-
   once-to-stderr reaches humans, not the *calling process*) — so a per-invocation
   cron can't tell "logged" from "silently dropped." Surfacing the sink's *existing*
   sync success/failure as a **return value** is the same move that justified
   `captureSync` itself (§14.1: "surfacing the sink's existing synchronous writer"):
   - **Does not break "never throws."** Returning a status is the opposite of
     throwing — the sacred contract holds.
   - **Mechanism, not policy.** flightlog reports *did the write land*; the adopter
     decides what to do (retry / exit non-zero / alert). Clean split.
   - **Additive.** `void` callers ignore the return; no existing behavior changes.

   **Open spec questions to lock before building (this is a `→ void` contract
   change, hence a PRD event, not a quiet add):**
   - Return shape: `boolean` (landed?) vs `{ ok: boolean, errno?: string }` (lean
     `{ ok, errno }` — the errno is already known at the failure site and costs
     nothing to surface).
   - Async asymmetry: `capture()` stays fire-and-forget `void` by design (an async
     path can't return a sync status, and a Promise would re-introduce the
     await-footgun captureSync exists to avoid). So **only `captureSync` gains the
     return** — defensible, but document the asymmetry explicitly.
   - Update the `→ void` lines in §6, `context.md` API, and the generated `.d.ts`
     (JSDoc `@returns`), plus a subprocess test asserting a forced write failure
     reports `ok:false`.
   Ships in 0.4.0 alongside any other additive work; until then the in-library
   signal genuinely doesn't exist and adopters rely on the stderr warn-once.

## 16. Security audit — 2026-06-01 (`/security`)

Full audit after the 0.4.0 work. The shipped library (`src/`) is sound — the one
catastrophic-for-a-log-format risk, **JSONL line/record injection, is provably
defended**: `JSON.stringify` escapes newlines and quotes, so an attacker-controlled
error *message* (or any context *value*) cannot forge a second line — verified with
a crafted `message` containing `\n{"kind":...}` yielding exactly one line. Secrets
(no `.env` tracked, none in `--all` history), zero prod deps (`npm audit` clean),
`0600` file mode, and the swallow-and-warn-once self-failure path all held. No
Critical/High/Medium findings. Most of the "recurring six" are **N/A** (no
datastore, principals, endpoints, or untrusted request handling — it's an
in-process local-file library). Four Low items; verdicts:

1. **L1 — `examples/ship.js` didn't enforce HTTPS → FIXED.** The reference uploader
   `fetch`'d whatever `endpoint` string it got; a copied script pointed at `http://`
   would send error logs (potentially sensitive) in cleartext. Now **fails closed**:
   `shipOnce()` returns `{ error: 'endpoint must be https' }` and reads/sends nothing
   on a non-`https://` endpoint. Guard runs *before* consent (config error, not a
   read). Fix is in reference code adopters copy — worth doing even though it's not
   shipped in the package.

2. **L2 — context can clobber core record fields → DOCUMENTED (by design).** `...context`
   is merged last (locked record shape, §6), so a context/`extra` key named
   `ts`/`kind`/`name`/`message`/`stack` overwrites the real one (confirmed live).
   Intended for deliberate context, but `capture(err, untrustedObject)` lets crafted
   *keys* forge the fields you'd trust during an incident. Not a code change — the
   merge order is locked — but a **gotcha** added to `context.md`: pass allow-listed
   fields, never a raw request/payload object. (Distinguished from values, which are
   always safe via JSON-escaping — the L-clean injection result above.)

3. **L3 — `examples/read.js` printed an unescaped `jq` hint → FIXED.** The
   convenience "jq equivalent" interpolated filter values and the path into a shell
   string with no quoting (printed, never executed — hence Low). Now jq string
   literals are emitted via `JSON.stringify` and both the program and path are POSIX
   single-quoted, so a hostile `--kind` value or a path with spaces is paste-safe.

4. **L4 — log *parent dir* created with default (umask) perms → ACCEPTED.** The file
   is `0600`; only the directory follows the umask, so existence/filenames may be
   discoverable on a shared host but contents are not. The library can't safely
   tighten a directory the adopter may have pointed at an existing shared location;
   the threat model already says keep logs off shared paths. No change.

5. **L5 — `examples/read.js` printed raw control chars from log content → FIXED**
   (second audit pass, 2026-06-01). The default human formatter `summarize()`
   interpolated `ts`/`kind`/`name`/`message` raw, so a logged error message carrying
   an `ESC`/`CR` (error messages routinely embed attacker-influenced input) reached
   the terminal verbatim — a viewer could be made to spoof or hide output during
   incident review. Stress-tested: every C0 control, `DEL`, and the C1 `0x9b` CSI
   leaked raw (and clobbered `ts`/`kind` via L2 too). Now `summarize()` renders
   C0/DEL/C1 as visible `\xNN`; printable UTF-8 and normal lines are untouched, and
   the `--raw` path was already safe (`JSON.stringify`). This is the in-scope
   *injection* class for this target (terminal-control-sequence), distinct from the
   JSONL line-injection that stays defended — values are escaped *on disk*; the leak
   was only when a reader un-escaped and printed them raw. Locked by two tests.

**Testing-scope note.** §9.5 scoped tests to `src/` (the shipped lib). The L1/L3
fixes live in repo-only `examples/`, and because adopters *copy* those scripts, the
security guards are now regression-locked in `test/examples.test.js` (10 tests:
HTTPS-fail-closed incl. guard-before-consent and offset-only-advances-on-ack; the
paste-safe jq hint executed through a fake `jq` to prove no injection; control-char
neutralization in `summarize()` (L5); plus read.js filter/torn-line behavior). This
is a deliberate, bounded extension of the test surface to cover security-relevant
reference code — not a general policy to test every example. Suite: 38 → 48.
